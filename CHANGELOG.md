## Unreleased

- **Fixed: an overlay-only project would not play in the editor — space and the play button did nothing, on a timeline that displayed the correct duration and reported no error.** A project with no video clips on `tracks[0]` is a "canvas project" and runs the preview's own wall clock, whose end-of-timeline ceiling was computed from the *overlay* tracks alone (`tracks.slice(1)`). Skipping track 0 is safe only while it holds the primary footage; in canvas mode it does not, it holds content — the background images, and on an agent-authored project frequently the overlays themselves. A project emitted by the animations workflow is routinely ONE track holding nothing but overlays, so for exactly those the ceiling summed to `0` and the transport started and stopped within a single frame: the first tick clamped the playhead to `0` and cleared the playing flag. Nothing threw and nothing was logged, because nothing failed — the clock had been told the project was zero seconds long, while the duration readout (computed separately, across all tracks) went on showing the true length. The same defect stopped a canvas project early whenever a track-0 background image outlasted the last overlay. Both playback paths — the WebCodecs engine and the legacy `<video>` player — carried it independently, so the automatic fallback between them could not mask it; both are fixed. The ceiling now spans every enabled track, track 0 included, which is what the preview's overlay layer has always drawn in canvas mode; the transport was the sole component disagreeing with what was on screen. Verified end to end in the browser on the project that surfaced it: before, the playhead sat frozen at `0:00.0` against a `1:50.0` duration; after, it advances in real time and space pauses and resumes. Audio deliberately stays out of the canvas ceiling — that canvas/video divergence is recorded in `timeline-core`'s `durations.js`, and unifying it would change playback length for every existing canvas project. No project files change: no migration, no re-save, and any project that played correctly before plays identically. ## v4.2.0

- **Fixed: overlays in 1080p exports were softer than the same design looks in a browser, because the renderer drew them at 4K and then threw the extra detail away.** Overlays are drawn by a headless browser and composited onto the video. The design canvas is deliberately fixed at 1080 on the short edge so overlay JSX coordinates mean one thing regardless of output size, and the browser was then told, unconditionally, to draw at `deviceScaleFactor: 2` — 2160 short edge, every time. That is exactly right for a 4K export, where 1080x2 is the finished size and the composite is an identity; it was measured and shipped for precisely that case. It was never made conditional on output size, so a 1080p export captured at 2160 and then downscaled 2:1 at composite time. Downscaling is a blurring operation, so text and fine lines arrived softer than the pixels the browser actually drew. The capture scale is now derived from the project's resolution and clamped to `[1, 2]`: 4K still captures at 2 (identity, unchanged), 1080p captures at 1 (native, no resample), a 1440p project gets a fractional 1.333, and a sub-1080 project clamps to 1 rather than capturing below the design canvas. Measured on a four-overlay 1920x1080 SDR excerpt against the browser's own capture as ground truth: fine detail up 36.1%, and 92.5% of what the browser drew survives to the file instead of 68.4%, for under 3% more bytes. On a full 53.8s ten-section export of the same project the gain is larger and the cost is too: fine detail up 41.4% on average with every section improved (best +61.8%, worst +10.6%), for **13.1% more bytes** — sharper edges are genuinely harder to compress, and the excerpt's sub-3% figure is not representative of a whole export. Nothing about how overlays are authored changes — the design coordinate system is untouched, so no existing overlay moves, resizes, or re-lays-out; only the sampling grid it is captured on changes. Capturing a quarter as many pixels per frame at 1080p should also cut render memory substantially, on a path where a large project had previously exhausted memory at high worker counts. **This changes the output of every existing 1080p project that sets `settings.resolution`**: the text is sharper, but it is genuinely different rather than strictly better, and anyone who preferred the softer averaged-down look will notice. A project with no `settings.resolution` set keeps the old unconditional 2x deliberately — the true output size isn't known until video sources have been normalized, and probing them earlier reads coded dimensions that are transposed for rotated footage, so those projects forgo the improvement rather than risk a swapped export. No encoder settings changed; a seven-cell spike over the delivery encode (CRF, dither, scaler flags, 10-bit, 4:2:2, and a 4:4:4 intermediate) was run in full first and every cell was a no-op or near enough, with the best available gain measuring +0.0008 SSIM. - **Fixed: two audio tracks in the editor could silently collapse into byte-identical copies of each other, or one edit could fan out and clobber every other audio track in the project.** `docs/schemas/project.md` never required `id` on an `audio.tracks[]` entry — only `src` is required, and neither the schema doc nor `engine/validate.py` backfilled one — but the editor's `AudioTrack` type declares `id: string` required, and both the auto-crossfade pass (runs unconditionally whenever two audio tracks overlap, no edit needed) and every audio mutation (`updateAudioTrack`, the track-replace path, multi-select mute/delete) address a track by matching or keying on `id`. With every track's `id` reading as the same `undefined`, a `Map` keyed by id collapsed to one entry and handed that same track back for every original one — turning a two-track music bed into two copies of the same track the moment they overlapped — and an `===` match on `id` was true for every track at once, so dragging a single fade handle applied the edit to all of them. Audio tracks now get a real, distinct id backfilled on project open (`normalizeAudioTracks`, mirroring the existing visual-track and caption-id backfills — same "same object back when already converged" contract, so an unaffected project triggers no save), and both `computeAutoCrossfade` and `updateAudioTrack` normalize defensively on their own besides. Existing real ids (e.g. `vo-01` from `project/init.py`) are preserved untouched; only a missing or duplicate id gets a generated `aud-<n>` replacement. - **Added: overlapping two clips or two overlays on the same track now dissolves between them, in the editor's preview and in the final export alike — instead of the overlap being forbidden outright, or the two engines silently disagreeing about what it should look like.**

  A partial overlap between two neighbouring items on one track is now legal, and the overlap itself *is* the transition: the render and the editor's own preview engine both composite a dissolve across the shared span, from one shared blend factor. Two shapes remain errors, both still surfaced as `visual_track_overlap`: **containment** (one item's span fully swallows the other's, identical spans included — there is no "from" and "to" to blend between) and **three or more items live at the same instant** (a transition is a pair; put the extra item on its own track). This only loosens overlay tracks (`tracks[1+]`), which used to forbid any overlap at all; `tracks[0]` never enforced an overlap check to begin with and still doesn't.

  Two different mechanisms carry the blend, because a clip and an overlay can't share one. An overlapping **overlay** pair gets real, editable `opacity` keyframes: the editor writes complementary `1 → 0` / `0 → 1` curves across the overlap, each marked `"origin": "crossfade"`, and the moment the operator edits one by hand it loses that marker and is never rewritten again. An overlapping **clip** pair (`tracks[0]`, or an `image`/`video` item on an overlay track) blends structurally instead, with nothing written to the project file: the resolver derives the blend purely from the pair's overlap span, and both the render and the editor's preview engine read that same factor to composite the two frames. This isn't a design choice — ffmpeg applies a clip's alpha through `colorchannelmixer=aa=`, whose `aa` option is a literal `<double>` with no expression support at any evaluation mode, so a clip's alpha has never been able to vary over time through the render's filter graph, and still can't; the clip's own audio crossfades too, via a complementary volume ramp driven by the same progress factor.

  An overlay marked `opaque: true` covers the whole frame, so the renderer skips compositing whatever is beneath it — fading it out mid-transition would reveal that skipped black, not the item underneath. When the outgoing side of a pair is opaque it now holds at full opacity for the whole transition instead, with only the incoming item fading in over it, which is what makes the dissolve read as smooth instead of dipping through black. That only works because the renderer's alpha-capture path (`captureOptionsFor`) now switches an opaque overlay to a transparent (`yuva420p`, `omitBackground`) capture whenever it's the *incoming* side of such a pair — otherwise it has no alpha of its own to fade in with, and would composite against the browser's own page background instead of the section beneath it.

  **This also fixes a real, pre-existing bug — not only adds a feature.** Two overlapping `tracks[0]` clips already disagreed with themselves: the editor's preview showed the earlier clip for the whole overlap and then hard-cut, while the export composited the later clip on top of it instead — measured bit-exact during the spike, the old encode of the overlap segment came out byte-identical to the later clip rendered alone. Anyone who has ever overlapped two primary clips hit this without knowing it. Both ends now blend from the same resolver-supplied factor, so preview and export finally agree.

  One measured implementation detail worth recording: the render's blend expression is emitted in the folded form `A+(B-A)*p`, deliberately, never the algebraically identical `A*(1-p)+B*p`. On a real 4K HDR overlap segment, against this feature's 2x render-time budget, the unfolded form measured 1.86-2.01x the hard-cut baseline — straddling the gate — while the folded form measured 1.35-1.49x for byte-identical output (verified per-pixel over the whole frame).

  The automatic fade is written by the editor only. A project authored directly — a script, an agent — gets no automatic `opacity` keyframes for an overlapping overlay pair and must write its own; see "Transitions" in `docs/schemas/project.md`. - **Fixed: an audio track placed anywhere other than the very start of the timeline could export as complete silence.** Not quiet — digitally silent, with the render reporting success. Every track is pushed into position with `adelay`, which prepends `start` seconds of silence, so every filter chained after it is timed against the padded stream. The fade-out's `st=` was being computed in track-local time (`(end - start) - fadeOut`) instead, so for any track with `start > 0` it fired `start` seconds early — and once `afade=t=out` completes it holds zero for the rest of the stream. A music bed running 27.67s→53.8s with a 3.08s fade-out reached zero gain at 26.13s, a second and a half *before* its own audio was due to begin, so its entire 26.1s was multiplied by zero, and the deliverable measured -91 dB across its last 24 seconds once the voiceover underneath it ended. `afade=t=in` had the same root cause — carrying no `st` at all, it ran at stream time 0, entirely inside the silent padding, so an offset track jumped in at full volume with no fade. Both are now expressed in stream time (`st = end - fadeOut` and `st = start`) by one shared helper rather than the two byte-identical copies that previously carried the bug in both the plain and the audio-ducking branches. The same fix covers a second route to the identical symptom: a track with no `end` (legal, and never trimmed on by the renderer) was treating the missing value as 0, placing its fade-out at `st=0` and silencing itself for the whole stream — reachable just by dragging a fade-out grip on an end-less music bed. Such a track now gets no fade-out at all rather than one anchored to nothing. Tracks starting at 0 are unaffected and render byte-for-byte identically — verified by decoding a mix to raw PCM before and after and comparing hashes. No project files need migrating and no audio settings change; projects that were silently losing audio simply start producing it again. This path had **no end-to-end test coverage at all** (every compose fixture used an empty track list, and all five unit tests sat at `start: 0` — the four that set a fade landing on the one value where the broken and correct expressions are numerically identical — which is how it survived a dedicated audit); it now has both an offset-track unit fixture and a real render that asserts on measured output level. (`montaj_assets/render/mix-audio.js`, `montaj_assets/render/test/mix-audio.test.mjs`, `montaj_assets/render/test/integration-compose.test.mjs`, `montaj_assets/timeline-core/KNOWN-DIVERGENCES.md`)

## v4.1.1

- **Fixed: a failed render told a remote caller nothing but "exit 1".** The render subprocess's stderr — which carries the actual cause, whether that's the renderer's own error JSON, an ffmpeg failure, or a missing file — was captured into the job's line buffer and then never exposed by `GET /api/projects/:id/render/status`, so anything driving a render over HTTP (an agent through a connector, a mobile download button) saw only `Render failed (exit 1)` at phase `preparing` and had no way to find out more. In practice that cost a real user an hour of guesswork on a project whose only fault was a project status the renderer declines to render, which the log had said outright from the first attempt. A failed status now also carries `log`: the last 40 stderr lines, which is where the cause always is. Only on failure — a running or successful render reports no log, since the SSE stream already carries lines live for anyone watching one in flight. (`serve/routes/projects.py`, `tests/test_render_async.py`)

## v4.1.0

- **Added: a Homebrew install of montaj now provisions its zscale-capable ffmpeg automatically, so `montaj install ffmpeg` is no longer a required first-run step.** montaj's HDR pipeline needs an ffmpeg built with `zscale` (libzimg), which no mainstream package manager ships, not even Homebrew's. Previously, after `brew install montaj` you also had to run `montaj install ffmpeg` yourself, or HDR conversions hard-failed with a `zscale_required` error the first time you hit them. The Homebrew formula now fetches that same pinned, checksum-verified static build as a Homebrew resource during `brew install` and stages it inside montaj's own install directory, so it's just there after the formula finishes. The resolver's lookup order gained a step for it: `MONTAJ_FFMPEG` env override, then the managed directory from `montaj install ffmpeg`, then this new bundled copy, then a bare `ffmpeg` on your `PATH`. `montaj doctor` now passes as soon as any of those tiers resolves to a zscale-capable binary, and only points you at `montaj install ffmpeg` when none do. This also removes a real piece of friction: the formula no longer depends on Homebrew's own `ffmpeg`, so a pinned or held Homebrew ffmpeg can no longer block `brew install montaj` with a "you must `brew unpin ffmpeg`" error. None of this touches an ffmpeg you already have installed yourself, montaj simply stops reaching for it, and the bundled binary is deliberately not linked onto your `PATH`, so your own `ffmpeg` command keeps working exactly as before. `montaj install ffmpeg` still exists for the explicit or offline case, and pip installs are unaffected, there's no bundling on that path, so `montaj install ffmpeg` remains the first-run step there. The trade: montaj no longer inherits Homebrew's automatic ffmpeg security updates, but montaj already owned this exact pinned build for the managed-install path, and a new test keeps the pin in the formula and the pin in montaj's own downloader from drifting apart. (`lib/common.py`, `cli/commands/doctor.py`, `tests/test_common.py`, `tests/test_ffmpeg_pin_sync.py`, and `Formula/montaj.rb` in the separate `homebrew-montaj` tap repo)

The ghost now resolves to the exact video row the finished clip will land on, through a shared rule (`resolveDropTrackIndex`) that both the ghost and the placement use, so it can never sit on an overlay or audio row again. The Montaj sidecar container ships the Docker default 64MB `/dev/shm`, which a 4K (2160×3840) render overruns — Chromium exhausts it and crashes mid-render, so the render dies with no output (and leaks zombie `chrome_crashpad` processes). This makes renders independent of the container's `/dev/shm` size; no Docker/compose change is required.

## v3.2.3

- **Render: a render survives a dropped client connection instead of being killed mid-flight.** A manual render streamed its log over SSE and was tied to that request: on `request.is_disconnected()` it called `kill_tree()`. But a multi-minute render (e.g. 16 Puppeteer overlay segments) streamed through the Hub proxy + Cloudflare tunnel outlives the tunnel's ~100s wall — the tunnel cuts the long-lived stream, the sidecar saw the disconnect, and **killed the render before it produced any output** (it stalled at whatever segment it had reached, with `/outputs` empty). Renders now run **detached**: a background task (`_run_render_detached`) owns the subprocess and the `_active_renders` / `_render_procs` slot until the render *actually finishes*, independent of any client. The SSE endpoint is a pure **viewer** over the render's live log + terminal state — a disconnect just stops viewing; the render keeps going, the output lands, and clients reconnect / poll `/outputs` for it. An explicit `POST /projects/{id}/render/cancel` is now the only thing that aborts a render (the editor's Cancel button calls it). Pairs with the supersede fix (now in v3.2.2): a render can't be orphaned by a dropped connection, and if one ever wedges, the next render supersedes it. Covered by `tests/test_render_detach.py`.

- **Render: `sourceCrop` is applied again — the source video reframe is no longer dropped.** `collectAllItems` in `render.js` builds each video item from a whitelist of fields and never copied `sourceCrop` / `sourceWidth` / `sourceHeight`. The segment encoder's crop branch (`buildVideoItemFilterParts`) keys on exactly those three fields, so with them missing the crop was silently a no-op: the full source frame (e.g. a 3840×2160 16:9 talking head) was letterboxed into the portrait output canvas instead of being reframed to the 9:16 slice the clip's `sourceCrop` defines. Because `normalize_window` keeps the cache at full source dimensions (it does NOT bake the crop into `normalizedSrc`), the crop *must* be applied at encode time — forwarding these three fields restores it. The `sourceWidth/sourceHeight` carried on the item match the normalized cache's dimensions, so the crop math is correct whether the chosen src is the original or the `normalizedSrc`.

## v3.2.2

- **Render: a hung or abandoned render no longer wedges a project's render slot.** A manual render is guarded by an in-memory `_active_renders` set in the serve layer, released in a `finally` when the SSE stream ends. But if the render subprocess hangs (produces no more output and never exits) or its stream is abandoned mid-flight (the Hub proxy / Cloudflare tunnel cut the connection while the generator was blocked on `readline()`), that `finally` never runs — the slot stays occupied and every subsequent `POST /projects/{id}/render` returns HTTP 409 `concurrent_render` until the sidecar process restarts. (The `render.js` lockfile self-heals via dead-PID reclamation; the in-memory serve guard did not.) A new manual render now **supersedes** a tracked previous one: it kills the previous render's whole process group via `killpg` (so orphaned ffmpeg / headless-browser children die too) and takes over, so re-clicking Render always works. A slot held by a non-render job (e.g. a carousel auto-render) still blocks with 409. The render's `finally` releases the slot only if it's still the tracked process, so a superseding render isn't clobbered. New `_render_procs` registry + `_supersede_active_render` helper; covered by `tests/test_render_supersede.py`.

- **New `generate_captions` step (CLI + registry).** Orchestrates the full caption pipeline in a single async step: `extract_keeps` → `materialize_cut` → `transcribe` → `caption`. Writes the final caption data to `project.captions`, making it available for render and the editor preview. Lets agents generate captions via `montaj_step` without hitting the SSE proxy wall — the step runs server-side and can be polled for completion like any other registered step.

- **Editor: a stray string `googleFonts` no longer breaks the whole overlay layer.** `ensureGoogleFontsLoaded` (shared by the video overlay layer and the carousel overlay render path) guarded with `if (!googleFonts?.length) return` and then called `.map`. If an item's `googleFonts` was persisted as a bare string (e.g. `"Anton"`) instead of the typed `string[]` (`["Anton"]`), the non-empty string passed the `.length` guard and `.map` threw `n.map is not a function` — surfacing as a cryptic `overlay error: <file>.jsx` that broke the entire `OverlayItemsLayer` at the playhead. The helper now coerces a string into a family list (splitting comma-separated values) and bails on anything that isn't a non-empty array; proper-array behavior is unchanged. Covered by new unit tests in `montaj_assets/editor/src/lib/__tests__/google-fonts.test.ts`.

## v3.1.0

- **Configurable source normalization (`eager`/`lazy`).** The clips workflow imports lazily — instead of re-encoding the entire source up front, each clip's window is normalized on demand (new `montaj step normalize_window`, a `normalizedSrc` per-window cache on `tracks[0]` items, and a `--normalize eager|lazy` flag / workflow-recipe field). `eager` (default) preserves the existing behavior: full-source re-encode at import. `lazy` skips it; render and preview resolve `normalizedSrc` first, falling back to `src`.

- **`clips` workflow: long-form horizontal source → series of short vertical (9:16) clip projects.** The `find_clips` agent task transcribes and samples the source video to identify the best moments, then fans each moment out into its own project. A new `sourceCrop` primitive on video items handles vertical reframing — choose from `zoom` (center crop filling the frame), `thirds` (source floated in the top portion of the 9:16 canvas over a background fill, preserving spatial context), or `mix` (cropped source at ~50% scale occupying the top half, leaving the bottom for captions or overlays) — and is configurable in the editor. For local fan-out the source file is shared by symlink rather than copied, so disk usage stays flat.

- **Skills transport/domain split (Phase 1).** Domain skills (`select-takes`, `overlay`, `write-overlay`, `image-search`) are now transport-agnostic; a new `skills/native/SKILL.md` owns the Montaj-specific CLI + HTTP interface; and `skills/_contract/SKILL.md` defines the shared vocabulary contract all skills reference by name (`load skill \`x\``). The root `skills/SKILL.md` is a thin dispatcher (detects MCP / HTTP / CLI context); `skills/serve/SKILL.md` was folded into `native` and removed. A new `@bycrux/montaj-skills` npm package (`montaj_assets/montaj-skills`) publishes the transport-agnostic domain skills + contract for external consumers; release via `scripts/release-montaj-skills.sh` (tags `montaj-skills-v*`).

## v2.7.0

### Added
- Per-request credential passthrough for `POST /api/steps/:name`. A reserved top-level `credentials` field in the step request body — shaped `{provider: {key: value, ...}, ...}` — is validated against the `KNOWN_PROVIDERS` allowlist in `lib/credentials.py` (`build_env_overlay`) and, on success, injected as environment variables into that single step subprocess only. The field is popped from the body before param validation and CLI-arg construction ever see it, so it can never collide with a schema param, leak into argv, or be echoed back in a validation error; the server's own environment (`os.environ`) is never mutated. Unknown providers, unexpected keys, and non-string/empty values are rejected with a 422 `invalid_credentials` before the subprocess is ever spawned, with value-free error messages (CredentialError messages name the offending provider/key but never a value). The primary use case is keyless multi-tenant serve deployments: the Hub (or any caller) passes the tenant's credential at call time rather than pre-configuring a per-tenant credentials file on the Montaj server. Local `montaj credentials`-file behavior is completely unchanged — when no `credentials` field is present the step subprocess inherits the server's environment exactly as before. Step error responses are additionally scrubbed of injected passthrough values — if an upstream provider echoes the caller's key in its error body (OpenAI does), the value is replaced with `[redacted]` before the 500 detail leaves the server; ambient/local credentials are untouched by the scrubber.
- New step `search_images` — searches for licensed images on Wikimedia Commons or TheSportsDB and prints a JSON object `{"results": [...]}` to stdout. Each result carries: `title`, `url`, `width`, `height`, `mime`, `license`, `artist`, and `source` (`"commons"` or `"sportsdb"`). Params: `query` (required), `provider` (enum `commons|sportsdb`, default `commons`), `limit` (int, default 10, max 30). - `montaj credentials` STILL echoed `^M` after Enter on the provider-selection prompt for the same users the v2.6.1 fix was supposed to help — confirming the v2.6.1 diagnosis was wrong. The v2.6.1 entry blamed ANSI escape codes in the prompt string confusing GNU readline's column tracking and "fixed" it by writing the prompt directly to stdout and passing an empty string to `input()`. That fix landed on the Homebrew install, ran on the same affected users' machines, and made no difference. Actual root cause, found by `import readline; print(readline.__doc__)` on the Homebrew install: Homebrew's `python@3.12` (the install path montaj ships through) is compiled against **libedit**, not GNU readline. The `readline` stdlib module on this build returns *"Importing this module enables command line editing using libedit readline"*. libedit is BSD's editline library, the same one Apple's system Python uses; it ignores GNU readline's `\001`/`\002` zero-width prompt markers entirely, which is why the prior fix's premise — that the line-editor was over-counting visible prompt width — was a non-issue on this build in the first place. Actual fix replaces `input()` with `sys.stdin.readline().rstrip("\r\n").strip()` at `cli/commands/credentials.py:120` (the provider-selection prompt). `sys.stdin.readline()` is a plain stdio read that bypasses `PyOS_Readline` entirely — libedit is never invoked for this prompt, the tty stays in its caller-configured mode, and there is no line-editor terminal prepping to misconfigure CR echo. The trade is the loss of arrow-key editing and history for this one prompt, which is fine for a number selector. The `_read_secret` fallback `input()` at line 247 is left untouched: it only fires when `getpass.getpass()` raises `EOFError`/`OSError` (i.e. non-tty environments), where libedit isn't engaged anyway. The primary `getpass.getpass(prompt)` call is also untouched because it uses its own raw tty loop (open `/dev/tty`, disable `ECHO` via `tcsetattr`, plain `os.read`), bypassing `PyOS_Readline` and libedit entirely. The misleading "ANSI in prompt" comment block introduced by the v2.6.1 attempt is replaced with a comment that names the actual cause (libedit terminal-prep + `^M` echo) and explicitly notes the prior wrong attempt for future-reader clarity. ### Fixed
- `montaj credentials` echoed a literal `^M` character after the user typed a number and pressed Enter at the provider-selection prompt, on certain terminal + Python combos (some tmux configs, IDE-embedded terminals, Windows Terminal over SSH). Root cause was raw ANSI escape codes embedded in the prompt string passed to `input()` in `cli/commands/credentials.py::handle` (`input(f"  Which provider? {_dim('(...)')}: ")`). Python's `input()` routes the prompt through `PyOS_Readline`, which on most builds hands the string to GNU readline (Linux, Homebrew Python on macOS) or libedit (macOS system Python) so the user can arrow-key edit and use history. The line-editor library tracks the cursor's visible column by counting the prompt's character width — but it counts the raw bytes of the ANSI escape codes (`\033[2m`, `\033[0m`) as visible characters, even though they render as zero width on screen. GNU readline exposes `RL_PROMPT_START_IGNORE`/`END_IGNORE` (`\001`/`\002`) markers to mark zero-width regions, but the credentials code didn't use them; libedit doesn't support those markers at all. With the column miscounted, the line-editor emits a bare `\r` when the user presses Enter to "return to column 0 before printing the newline." On terminals where the `ONLCR` output flag isn't translating that lone CR back to CRLF (some tmux configs without `default-terminal "screen-256color"`, VSCode integrated terminal in certain modes, Windows Terminal over SSH, mosh in some configurations), the bare CR echoes literally as `^M`. macOS Terminal.app, iTerm2, and gnome-terminal masked the issue with their pty defaults, which is why the bug wasn't visible to all users. Fix writes the colored prompt directly to `sys.stdout` first and then calls `input()` with an empty prompt, so the line-editor library sees a zero-width prompt and its column tracking is correct regardless of any ANSI bytes that preceded the input call. The `_read_secret` fallback path at `cli/commands/credentials.py:224-226` already followed this pattern; only the provider-selection prompt at line 103 had the leak. The primary `getpass.getpass(prompt)` call in `_read_secret` is unaffected by this bug because `getpass` on Unix uses its own raw tty loop (write prompt, disable ECHO, read line directly from `/dev/tty`) rather than `PyOS_Readline`, so ANSI in its prompt doesn't trigger column-tracking miscounts. - Final-rendered MP4s could show a short black frame at certain clip transitions even though the editor's preview rendered the clips continuously. Fix replaces the float-gap comparison with an integer frame-index comparison: `Math.round(a * fps) === Math.round(b * fps)` is cancellation-proof and semantically identical for the "within ~1 frame" case the snap is supposed to catch. - Audible "mic pops" at every intra-clip overlay start/end boundary in the final-rendered MP4 — distinct from a normal scene cut, present even after the visual sub-frame quantization fix landed, loud enough on speakers to be obvious. Diagnosed by probing consecutive-sample deltas in the rendered PCM around four representative boundaries in a 4K HDR project: intra-clip seams (where the audio should be perfectly continuous because both sides come from the same clip recording) produced max deltas of 1666–2356, while the natural inter-clip cut produced only 1382 — i.e. the per-segment audio handoff was louder than an actual scene cut. Root cause was the audio stream-copy fast path in `montaj_assets/render/encode-segment.js::encodeSegment` Step 5 (the `audioLabels.length === 1 && streamCopyCandidates.length === 1` branch). For every segment containing exactly one unmuted video item sourced from an `_audioclean.mp4` file with `volume=1` — which is almost every intra-clip segment, since track 0 never overlaps with itself — ffmpeg was invoked with `-ss <segStart> -t <duration> -i <_audioclean.mp4> -c:a copy`: the demuxer seeked to the nearest AAC frame at-or-before `<segStart>` (AAC frames at 48 kHz are 1024 samples = 21.3 ms, so the seek landed up to ~21 ms early), stream-copied the AAC packets into the per-segment MP4, and wrote an `edts/elst` edit list marking the pre-seek samples as "skip on playback." The `-f concat` demuxer in `compose.js::compose` then re-encoded audio at concat with `-c:a aac` — but the concat demuxer is known to drop per-input MP4 edit lists when audio is being transcoded ([ffmpeg ticket #2330](https://trac.ffmpeg.org/ticket/2330), [#7426](https://trac.ffmpeg.org/ticket/7426)), so the pre-seek (and post-end) samples from each segment's first AAC frame were decoded as real audio. The result was 10–25 ms of duplicated waveform at every intra-clip seam, which re-encoded into an audible click in the final AAC track. Inter-clip cuts (e.g. clip-2 → clip-3) popped less because the "duplicated" samples there are tail-of-clip-A overlaid on head-of-clip-B — two unrelated recordings whose combined energy is no worse than the cut itself; intra-clip seams popped worst because the duplicated samples are real voiceover overlapping itself. Fix replaces per-segment AAC entirely with PCM s16le: the stream-copy fast path and the `streamCopyCandidates` collection that fed it are deleted; the non-stream-copy encoder branch — previously `-c:a aac_at -b:a 192k -ar 48000 -ac 2` — is now `-c:a pcm_s16le -ar 48000 -ac 2`, with `atrim=0:${duration}` added to the per-item audio filter (before `asetpts=PTS-STARTPTS`) to make sample-exact duration trimming explicit in the filter chain rather than implicit in ffmpeg's `-accurate_seek` + `-t` defaults. PCM has no framing, no encoder priming, and no edit-list metadata, so per-segment encoder/container artifacts disappear at concat; an off-pipeline reproduction on a controlled AAC source measured the residual seam delta dropping from ~2400 (pre-fix) to ~500–800 (post-fix), with the residual coming from the AAC decoder's per-process seek precision rather than the priming/edit-list bug. The final `-c:a aac` pass in `compose.js` then re-encodes the joined PCM stream to AAC once at end-of-pipeline — exactly as before from the user's perspective (final output is still AAC 192 kbps), but now from a continuous-enough waveform instead of stitched encodes. The previous `aac_at`-under-libx265-4K-concurrent-encode AAC-bitstream corruption concern (which the deleted stream-copy fast path was originally introduced to work around) is also resolved in principle by this change: `aac_at` is no longer called at all, and the only AAC encode in the pipeline (the concat re-encode in `compose.js`) runs after every libx265 segment process has exited. With the items cleared, `encode-segment.js` Step 2's per-item audio-extraction loop never ran, so `audioLabels` stayed empty and Step 5 fell through to `anullsrc` — encoding the entire opaque window as silent 48 kHz stereo, which `compose.js`'s concat then baked into the final track. (Observed: a 13-clip explainer whose four opaque "how the exploit works" animation sections covered ~22 s of timeline rendered with a 22-second silent gap spanning exactly that voiceover.) The fix decouples audio from video: `segment-plan.js` now **keeps** the active items under an opaque overlay and instead sets a new `opaqueVideo: true` flag on the segment; `encode-segment.js` reads `segment.opaqueVideo` and gates only the **video** compositing (the `buildVideoItemFilterParts` filter graph and image layering) behind `!opaqueVideo`, while still adding each clip's input (with its `-ss/-t` window, so the audio is correctly trimmed to the segment) and running the unchanged audio-extraction path. The opaque overlay still composites over the black canvas exactly as before, so the visual result is byte-identical — only the previously-discarded audio is restored. Image items under an opaque overlay are skipped entirely (they carry no audio); an opaque overlay over a true gap (no underlying items) still yields silence, which is correct. `opaqueVideo` defaults to `false` in the encoder, so any caller that doesn't set it — and the `sample-frame.js` mini-composer, which has its own single-frame path and no audio — is unaffected. Regression coverage added: `test/segment-plan.test.mjs` now asserts an opaque overlay keeps its items and flags `opaqueVideo` (the prior test asserting `items.length === 0` was updated to the new contract), and `test/encode-segment.test.mjs` asserts an `opaqueVideo` segment extracts the clip's audio with no `anullsrc`, does not composite the clip's video, and still emits silence when there are no underlying items. Full render suite (61 tests) green.

### Added
- Two new CLI commands and matching MCP tools for fast visual sampling without running a full render. `montaj sample overlay <overlay.jsx> --out <path.png>` renders one frame of a JSX overlay through the same `bundleComponent` + Puppeteer path the production renderer uses and writes a PNG — ~3s wall time. `montaj sample frame <project.json> --at <seconds> --out <path.png>` renders the fully composited frame at the requested timestamp (active video clip + active image items + active overlay JSXs, all at project resolution) — ~10–30s wall time depending on active overlays. Both are exposed as MCP tools (`sample_overlay`, `sample_frame`) registered in `cli/mcp_schema.py`, backed by two new Python step scripts (`steps/render/sample_overlay.py`, `steps/render/sample_frame.py`), each a thin wrapper around the new Node module `montaj_assets/render/sample-frame.js` (exports `sampleOverlay` and `sampleFrame`). The `--measure` flag on `sample overlay` triggers a Puppeteer DOM walk before the screenshot: every text-bearing element is visited, its `getBoundingClientRect()` value is read, overflow against the design canvas is computed (`overflow.{left,right,top,bottom}` in pixels), and the nearest ancestor with `overflow-x/y: hidden|clip|auto` is identified and surfaced as `clippingAncestor`. Stdout in `--measure` mode is a single JSON object `{"pngPath": "...", "measurements": {"anyOverflow": true|false, "viewport": {...}, "texts": [...]}}` — `anyOverflow` is the go/no-go boolean for cheap short-circuit checks in agent loops; per-element `overflow` values tell the agent which element failed and by how much. Without `--measure`, stdout is the PNG path + newline in both subcommands. Stderr carries progress; exit 0 = success, exit 1 = failure with `{"error": "...", "message": "..."}` JSON. Three filter-graph helpers — `buildVideoItemFilterParts`, `buildImageItemFilterParts`, `buildOverlayFilterParts` — were extracted from `montaj_assets/render/encode-segment.js` (previously inline at lines ~120–285) and exported so both the production render path and the new sample mini-composer share identical filter math; the extraction is byte-for-byte behaviour-identical for the production path — SDR projects produce the same render output as before this change, verified by the fact that `encodeSegment` now calls each helper via a one-line delegation. The sample module uses a content-hash cache under `${tmpdir()}/montaj-sample-cache/` with 24h GC, so agent write-sample-iterate loops (~30 cycles × 3s) don't pay redundant Puppeteer launches when the overlay file hasn't changed. HDR projects (`hdr_hlg`, `hdr_pq`): sample PNGs are tonemapped to sRGB BT.709 at output time (`zscale` chain identical to the one `embedThumbnail` uses for poster JPEGs) so agents see display-correct pixels; the production render still emits correctly-tagged HDR output. Video frame extraction in `sampleFrame` uses accurate seek (`-ss` AFTER `-i`) rather than keyframe seek, because an agent probing `--at 5.5` needs the actual frame at 5.5s, not the nearest keyframe up to 1s away (~5–10s cost accepted, already within the 10–30s wall-time budget). The `skills/write-overlay/SKILL.md` agent skill is updated with a new section teaching agents to run `montaj sample overlay <path> --measure` after every JSX write and act on `anyOverflow`, including the canonical Syne overflow case study — "RECURSIVE" at `fontSize: 160` measures ~933 px wide in headless Chromium's `sans-serif` fallback (what the editor preview shows) vs ~1594 px wide in Syne 800 (what the renderer loads from Google Fonts CDN), a 514 px right-edge overflow invisible to the editor. ### Fixed
- Editor preview now loads each overlay item's declared `googleFonts`, matching what the renderer does. Previously, the overlay preview path (`montaj_assets/ui/src/components/preview/OverlayItemsLayer.tsx::CustomOverlay`) never read `item.googleFonts` — only the editor's own `index.html` preloaded Inter and Space Grotesk, so any JSX overlay using a non-preloaded family (e.g. `fontFamily: '"Syne", sans-serif'`) silently fell through to the browser's `sans-serif` fallback in the preview, while the renderer (via `bundle.js::generateHtml`) correctly loaded the declared fonts from Google Fonts and rendered with them. Fix: a new module-level `ensureGoogleFontsLoaded(googleFonts)` helper in `OverlayItemsLayer.tsx` injects a `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=...&display=swap">` into `document.head` the first time each unique URL is seen, using the same URL format `bundle.js` generates so preview and render fetch identical CSS. `CustomOverlay` calls it via a `useEffect` keyed on `googleFonts`. - HDR projects (`hdr_hlg`, `hdr_pq`) now correctly composite still images embedded inside overlay JSX. Previously, sRGB PNG images referenced from a JSX overlay (e.g. `<img src="file:///abs/path/logo.png" />`) were loaded unmodified by Chromium, screenshotted with sRGB pixel values, and then tagged by the segment encoder as HDR-encoded output — so HDR-aware players (iPhone Photos, QuickTime, Instagram) interpreted the sRGB pixel values in the wider BT.2020/HLG or PQ gamut, producing images that looked dim, desaturated, or hue-shifted against the surrounding HDR footage. The fix is a render-time Puppeteer request interceptor in `montaj_assets/render/renderer.js` (`renderChunk`): when the project color space is HDR, `page.setRequestInterception(true)` is enabled before each page load; every local `file://` image fetch is caught, the source PNG is converted to an HDR-encoded 8-bit RGBA PNG via `lib/normalize_image.py` (new module, a sister to `lib/normalize.py`), and the converted bytes are returned as the response body. The conversion applies the same `zscale` transfer-curve pipeline used for video normalization — `sRGB → linear → 2× linear brightness boost → BT.2020/HLG (or PQ)` — with the `zscale` chain targeting the project's specific color space. The 2× brightness boost was chosen so that images visually match overlay text brightness: sRGB white reinterpreted as HLG already hits ~203 nits (BT.2408 graphics reference white), so a 2× lift in linear light brings a midtone image up to match. Cached output is written alongside the source as `<stem>_<colorspace>.png` (e.g. `logo_hdr_hlg.png`), keyed by color space so a project can switch between HLG and PQ without collision; cache invalidation is by source file mtime (same pattern as `_normalized_<colorSpace>.mp4`). Atomic rename (`write to .tmp → rename`) guards against partial-write reads from concurrent renders. SVG `<img>` references, remote (`https://`) image URLs, and non-image resources are passed through unchanged; remote URLs log a one-time per-host warning to stderr. On conversion failure the interceptor falls back gracefully (`request.continue()`) rather than aborting the render. Scope: **only images embedded inside overlay JSX** are converted — this is the path that goes through Puppeteer, and was the original source of the user complaint. Tracks-level `{type: 'image'}` items continue to flow through encode-segment's existing image branch unchanged (they get the pre-existing reinterpret-as-HDR treatment: bright, slightly hue-shifted). Overlay text, shapes, SVG, and captions are also intentionally untouched — they stay on the sRGB-reinterpreted-as-HDR path that produces bright, punchy output (deliberately preserved from v2.5.7 after earlier attempts to convert overlays were reverted). SDR projects are a complete no-op: `isHdr()` gates the interceptor and no Python is spawned. `lib/types/colorspace.py` gains an `is_hdr(key) -> bool` helper; `montaj_assets/render/color-space.js` gains the JS mirror `isHdr(key)`. Both are thin wrappers used to gate the interceptor and the Python module's validation. Also note: the JS-side cache-hit check uses `existsSync` + a source-mtime comparison so that replacing the source PNG on disk between renders invalidates the cached HDR PNG, matching the documented contract.
- Final-rendered MP4s now carry an embedded poster thumbnail, so Finder, QuickTime, iMessage, Slack, and most social previews show a representative frame instead of a black/blank tile before playback. Previously, both the per-segment-then-concat path (`montaj_assets/render/compose.js::compose`) and the lyrics drawtext fast-path (`montaj_assets/render/render.js`, `renderMode: 'ffmpeg-drawtext'`) emitted only video + audio streams, with no `attached_pic` stream — confirmed by ffprobe on existing `render/final.mp4` outputs. New exported helper `embedThumbnail(outputPath, colorSpace)` in `compose.js` runs as the final pipeline step in both paths: extracts a single JPEG frame at 1.0s (falling back to frame 0 if the video is shorter than 1.0s or the seek fails for any reason), then re-muxes video + audio + JPEG into the same path with `-disposition:v:1 attached_pic`. Both passes are stream-copy on the AV tracks; the only encode cost is the single JPEG, so total runtime adds ~1s per render. HDR projects (`hdr_hlg`, `hdr_pq`) tonemap through `zscale=t=linear,format=gbrpf32le,zscale=p=bt709:t=bt709:m=bt709:r=tv,format=yuv420p` before the JPEG encode so the poster doesn't ship as washed-out HLG/PQ-misinterpreted-as-sRGB pixels. Failure is non-fatal: any ffmpeg error in either pass is logged via the existing `[montaj compose]` channel and the render returns the thumbnail-less file rather than aborting an otherwise-good render. No project.json schema change; thumbnails are now automatic on every render.

### Fixed
- Deleting a primary-track clip with ripple ("magnet") mode on now closes the gap immediately. Both delete paths — clicking the trash on a clip (`VisualTrackRow.handleDeleteOverlay`) and pressing Delete/Backspace on a selected clip (`Timeline.handleKeyDown`) — were producing the filtered tracks but skipping the `collapseGaps` pass that every other ripple-aware mutation (cut, split, resize) runs. The fix routes both deletes through the same `if (rippleMode) updated = collapseGaps(updated)` step. Previously users had to toggle ripple off and back on to trigger the collapse — the toggle-on branch in `ReviewView.handleRippleToggle` already runs `collapseGaps`, which is why the workaround worked.
- Project names (and other creation-time metadata) no longer get wiped when the agent saves the project. `PUT /api/projects/{id}` previously did a full replace — the agent's documented save pattern (`skills/serve/SKILL.md`) shows a minimal body like `{id, status, tracks}`, so the very first agent-driven pending→draft transition was stripping `name`, `workflow`, `editingPrompt`, `projectType`, `runCount`, `settings`, `assets`, etc. from `project.json`. The endpoint now top-level-shallow-merges the body into the existing project on disk, preserving any key the caller didn't send; to explicitly clear a field, callers must send it as null. UI savers were already spreading the full project, so this is a no-op for them — the fix only changes behavior for partial bodies. Existing projects already gutted on disk can be recovered with `git show <init-commit>:project.json` against the project's git history (every project workspace is its own git repo with a `init: new project` baseline commit).
- Editor zoom (cmd/ctrl + wheel) now zooms slower and stays pivoted on the cursor instead of snapping the pivot to the center of the viewport. The pivot formula in `useTimelineZoom.ts` was computing the correct content-fraction under the cursor but writing the new scrollLeft so that the pivot landed at `containerWidth / 2`, which only matched the cursor when the cursor happened to be centered — anywhere else, the zoomed-in region drifted relative to where the user pointed. Fixed to use the actual cursor offset for both reading the pivot fraction and reseating the scroll position, so the yellow hover indicator stays exactly under the cursor through the zoom. The wheel step also switched from a fixed ±0.5 per tick to a multiplicative `exp(-deltaY * 0.002)` factor — meaningfully slower at a typical mouse-wheel tick (~18% per click vs the old jump of half a zoom level), smooth for trackpad pinch (tiny deltaY → tiny step), and perceptually consistent across zoom levels.
- Three.js overlays now render at the same size in the live UI preview as they do in the final MP4. r3f's auto-measure (`react-use-measure`) was reading the canvas-host element via `getBoundingClientRect()`, which returns post-transform dimensions — and the UI preview wraps overlays in a `transform: scale(N)` design wrapper that fits the 1080×1920 design canvas into the preview pane. So an overlay container authored at design `width: 1080, height: 500` was measured as ~245×113 px, and r3f sized the WebGL viewport + camera frustum for that tiny region; the ancestor transform then scaled the rendered output by another `N`x, so 3D content appeared at ~5× shrinkage and visually off-center compared to the final MP4 (where the same JSX renders inside Puppeteer at the full 1080×1920 layout with no transform ancestor). Passing `resize: { offsetSize: true }` through r3f to react-use-measure was *supposed* to switch to `element.offsetWidth/offsetHeight` (layout-space, transform-agnostic), but in our nested-transform setup it didn't take effect. Fix: the preview Canvas wrapper now mounts a small `PreviewForceSize` child component inside the r3f scene that reads its parent div's `offsetWidth`/`offsetHeight` directly and calls `useThree().setSize(w, h, true)`, re-applying on any subsequent resize via `ResizeObserver`. Render context is untouched — Puppeteer's headless layout has no ancestor transform, so r3f's default measurement is already correct there.
- Renders triggered from the UI no longer corrupt segment audio. The UI's `RenderModal` (and its mobile/carousel siblings) fires `api.renderProject` from a `useEffect` on mount; React StrictMode's dev-mode mount → cleanup → mount cycle fires this effect twice synchronously, sending two `POST /projects/:id/render` requests to serve, which spawned two concurrent `render.js` processes against the same workspace. Both processes wiped each other's segment directory and stamped output to the same `final.mp4.segments/seg-NNNN.mp4` paths; with `-movflags +faststart` the trailing moov-relocation pass of one would seek through bytes the other was still writing, leaving ADTS framing intact but every AAC packet payload zero-filled — segments looked valid (`ffmpeg exit 0`) but failed decode at concat with "Reserved bit set" / "channel element X.Y is not allocated" / "Number of bands exceeds limit". Three independent defenses landed: (1) `render.js` lockfile acquisition switched from check-then-write to `openSync(lockPath, 'wx')` (POSIX `O_CREAT | O_EXCL`) — atomic at the OS layer, eliminates the TOCTOU race that let both processes write their PID; (2) `serve/routes/projects.py` `/projects/{id}/render` now tracks in-flight project ids in a module-level set and returns `409 concurrent_render` for any second request before spawning render.js — defense at the serve layer where FastAPI's single asyncio loop makes the set-mutation race-free; (3) all four render modals (`RenderModal`, `MobileRenderModal`, `CarouselRenderModal`, `MobileCarouselRenderModal`) wrap their cleanup in a deferred `setTimeout(..., 0)` so StrictMode's transient unmount is "rescued" by the next mount (which calls `clearTimeout`), while a real unmount lets the timer fire and cancels the render properly. The three defenses are layered: the UI fix prevents the duplicate request at the source, the serve dedup catches anything that slips past (e.g. a misbehaving CLI client), and the lockfile is the last line of defense at the OS layer.
- Renders no longer abort on iPhone source clips that contain an Apple Positional Audio Codec (apac) track alongside the regular AAC audio. iPhone .MOV files written by recent iOS releases include TWO audio streams: stream 1 is the conventional stereo AAC, stream 2 is apac (4-channel spatial audio, codec_tag `apac`). ffmpeg's default "best audio" stream selector sometimes picked stream 2, hitting the decoder on a codec it can't actually handle — producing mis-decoded packets with weird channel counts (4–11 channels) that downstream filters couldn't downmix to stereo, aborting the whole render with `Rematrix is needed between N channels and stereo but there is not enough information to do it`. Fix: encode-segment.js's per-source audio filter now uses `[idx:a:0]` instead of `[idx:a]`, which explicitly selects the FIRST audio stream of each input (the clean AAC on iPhone clips) regardless of ffmpeg's selection heuristics. Added `aformat=channel_layouts=stereo:sample_rates=48000` as a defensive downmix for any non-iPhone source with unusual channel layouts, plus belt-and-suspenders `-err_detect ignore_err -max_error_rate 1.0` and `-af aformat=channel_layouts=stereo` in compose.js's concat re-encode. Net result: audio renders cleanly from iPhone clips even when the apac stream is present in the source.
- Google Fonts in overlays and captions actually load now. The `googleFonts` array on overlay items (and on the top-level `captions` object) has been documented for a while, but the render bundler was silently dropping it — `bundleComponent` didn't read the parameter and the generated `<head>` had no font links. The bundler now emits the Google Fonts CSS2 `<link>` (plus the `preconnect` pair) and the shim awaits `document.fonts.ready` on the first frame so frame 0 paints with the requested font instead of a CSS fallback. A 5s timeout guards against network stalls — on timeout the render proceeds with whatever fallback the JSX declared rather than hanging. The captions spec in `render.js` also now forwards `googleFonts` through to the bundler so caption styles can use custom fonts the same way overlays do. Carousel renders (`render-carousel.js`) use a separate bundling path and do not honor `googleFonts` yet — that's a follow-up.

- URLs, methods, and headers are caller-supplied and opaque — S3 pre-signed URLs, R2, GCS, Azure SAS URLs, and custom webhooks all work without provider-specific code in Montaj.

### Fixes (caught during carousel work)
- **SSE multi-line frames.** `PUT /api/projects/{id}` and three sibling endpoints were publishing `f"data: {indent=2 JSON}\n\n"` over SSE. SSE requires a `data:` prefix per line, so the browser parser was splitting on every newline inside the JSON and logging `[sse] malformed project frame: {`. The optimistic instant-update was being dropped and the UI was relying on the watcher's later (single-line) re-broadcast to catch up. New `_sse_data_frame()` helper canonicalizes any payload to a single `data:` line; all four publish sites switched over.
- **Overlay compiler tolerates named exports.** `overlay-eval.ts` only rewrote `export default …` and let bare `export const X` / `export function X` / `export { X }` survive into `new Function(...)`, throwing `Unexpected token 'export'`. The browser preview broke for any overlay that exported anything other than the default component (e.g. an overlay declaring `export const staticFrame = 30` for the carousel renderer's static-frame default). Render path was unaffected (esbuild handled it). The compiler's normalize pass now strips the `export` keyword from named declarations and drops bare `export { ... }` lines.
- **Render dispatch by project type.** `POST /api/projects/{id}/render` hardcoded `render.js`, so calling it on a carousel project ran the video renderer (producing `final.mp4` from zero segments). The endpoint now reads `projectType` from `project.json` and routes carousel projects to `render-carousel.js` (mirroring `project/render.py`).

### Workspace flexibility
- Added: `--project-path` flag on `montaj init` (and CLI mirror) lets callers specify the project directory's relative path under the workspace, including multi-segment paths for subnested layouts (e.g. `--project-path=teamA/my-project`). `POST /api/run` accepts the same value as a `projectPath` body field.
- Added: `montaj serve` discovers projects at any depth under the workspace via recursive globbing — listing, get, stream, delete, update, versions, restore, rerun, and render all work regardless of how deeply a project is nested.
- Default `<date>-<slug>` directory naming is preserved when `--project-path` is absent. Fully backward compatible.
- Collisions on an explicit `--project-path` are hard errors (not auto-suffixed): `POST /api/run` returns 400 with `{"error": "project_path_exists", ...}`. Validation rejections (leading `/`, `..` segments, special chars) return 400 with `{"error": "invalid_project_path", ...}`.
