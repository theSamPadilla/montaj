# Changelog

## Unreleased

- **Added: a `search_news` step — Google News RSS search, fetched from the sidecar rather than from the caller.** Hub's `search_news` had been failing in production with `502 "News upstream returned 503"`; the cause was not an outage but an egress block. Google News refuses requests from Google Cloud IP space, which is exactly where Hub's backend runs, while returning 200 to the sidecar's Hetzner egress for the identical URL — verified from inside the running container on two different queries. The step fetches `news.google.com/rss/search`, parses the feed, and returns `{items: [{title, link, pubDate, source, snippet}]}`, matching the shape Hub already publishes to agents so nothing downstream has to change. `pubDate` is normalized from RFC-2822 to ISO-8601 UTC; `source` falls back through `<source>` → `dc:creator` → the link's domain; items without a title are dropped (Hub's contract marks it non-nullable). Snippets are stripped of markup before truncation at 280 characters — Google News wraps every `<description>` in an `<a href>` blob around a 300-500 character redirect URL, so truncating the raw body yields a snippet made entirely of href. A non-XML body — what Google returns when it throttles rather than blocks — fails as `upstream_unavailable` instead of surfacing a parser error. (`steps/media/search_news.py`, `steps/media/search_news.json`, `tests/steps/test_search_news.py`)

## v3.10.0

- **Fixed: overlay images in HDR (HLG/PQ) renders came out supersaturated with shifted hues — and gained selectable color mappings (`--image-tone`).** Three stacked defects in the sRGB→HDR image pre-conversion path (`lib/normalize_image.py`), all diagnosed against real projects and verified end-to-end with real segment renders. (1) The converter crashed on 4:2:0 JPEGs with an odd width or height (zimg: "dimensions must be divisible by subsampling factor") and segfaulted ffmpeg on palette PNGs, whose `pal8` pix_fmt fooled the `"a" in pix_fmt` alpha heuristic into the alphaextract branch; each failure made the renderer silently fall back to compositing the raw sRGB image into the HDR frame. The filter graph now normalises every source to `rgba` first — full-resolution, real alpha plane — so one graph handles all decoder formats and the alpha heuristic plus both branches are deleted. (2) The killer for *successfully* converted images: ffmpeg's PNG encoder tagged the converted file with `cICP`/`cHRM` chunks declaring BT.2020/HLG, so Chromium color-managed the image into its sRGB raster — mangling the very values the renderer's request interceptor depends on passing through byte-for-byte (measured ~19/255 mean per-channel shift; the module's contract was always an *untagged* PNG). The chain now wipes color metadata before the PNG encoder; a Chromium screenshot of the untagged output is pixel-identical to the served bytes. (3) With color now faithful, the original 2× "203-nit graphics white" brightness convention (BT.2408) turned out to be wrong for Montaj's look: overlay rasters land CSS graphics white at full HLG signal (~1000 nits), so colorimetrically-correct images read ~7× dimmer than the cards they sit inside. The brightness mapping is therefore a selectable **image tone**, implemented with exact per-pixel transfer math (ffmpeg `geq` in float — zscale's HLG npl/OOTF semantics are not the plain OETF these mappings need, verified to ≤1/255 against reference math): `vivid` (new default — colorimetric sRGB→BT.2020 with image white raised to match raster graphics), `broadcast` (the BT.2408 203-nit mapping, kept byte-identical), `punchy` (legacy tone — neutrals byte-identical to the old reinterpretation — with only the primaries corrected 709→2020), and `raw` (no conversion, the old oversaturated look). Selection: `montaj render --image-tone <mode>` > `settings.imageTone` in project.json > `vivid`; the editor surfaces it as a page-header setting (HDR projects only) with a description and a rendered generic example per mode, persisting to `settings.imageTone` (hosts place it via the new `onProvideImageTone` prop; the exported `ImageToneMenu` renders it). Conversion caches now carry the tone in their name (`<stem>_<colorSpace>_<tone>.png`), which also orphans all pre-fix `*_hdr_hlg.png` caches (they carried cICP chunks and must not be served) — re-renders regenerate automatically. Verified: a default render matches the vivid reference within 0.8/255 mean; `--image-tone punchy` matches its reference; `broadcast` output is byte-identical to the pre-tone fix. Remaining known second-order issue, not addressed here: the overlay FFV1 intermediate encodes RGB→YUV with swscale's default (untagged) matrix while the final stream is tagged `bt2020nc`, a few degrees of hue error — candidate follow-up. (`lib/normalize_image.py`, `montaj_assets/render/render.js`, `montaj_assets/render/renderer.js`, `cli/commands/render.py`, `project/render.py`, `montaj_assets/editor/src/schema.ts`, `montaj_assets/editor/src/video/{imageTone.ts,imageToneExamples.ts,ImageToneMenu.tsx,VideoEditor.tsx}`, `docs/schemas/project.md`, `docs/CLI.md`)

## v3.9.2

- **Captions: per-segment color.** `CaptionSegment` gains an optional `color` (CSS color), following the same resolution order v3.9.0 established for `offsetX`/`offsetY`/`scale`: absent → inherit the track-level `captions.color` → the style's own hardcoded default. All seven caption templates now read `seg.color ?? color` wherever their BASE text color is applied — `word-by-word`'s single active word, `subtitle`/`clean`'s text block, `karaoke`'s not-yet-spoken words, and `highlight-box`/`outline`'s unspoken words (both the no-words fallback branch and the main words branch). Per-style accent fields — `highlightColor` (karaoke), `activeColor` (pop), `accentColor` (highlight-box/outline), `backgroundColor` (subtitle) — are deliberately untouched, so a segment can recolor its base text without disturbing the active-word highlight. One template is a documented no-op: `pop` never rendered its `color` prop at all before this change (only `activeColor`, since it only ever shows the currently-spoken word) — `seg.color` correspondingly has no visible effect there, exactly matching what the pre-existing track-level `color` already did (or rather didn't) for that style. Editor: the captions panel's base-color swatch is now selection-aware — with a caption segment selected (`selectedCaptionId`) it shows and edits that segment's effective color (`seg.color ?? captions.color`) instead of the track's, and reverts to track-level editing the moment nothing is selected. The live/commit split mirrors the existing swatch exactly (see the "two undo steps" fix below in v3.9.0): `onChange` previews through `onProjectChange` with only the target segment patched (track-level `color` left alone), `onBlur` commits through `onCaptionSegmentChange` — the single-segment patch channel edge-drags and text edits already use — instead of the whole-track `onCaptionEdit`, so one color pick produces exactly one undo step, never two. `CaptionEditPatch` (`= Partial<CaptionSegment>`) picks up `color` automatically, no separate type change needed. The ffmpeg `drawtext` render branch is unchanged: it has no per-segment concept and keeps honoring only the track-level `color`. ## v3.9.1

- **Fixed: dragging a caption segment did not snap to the frame's centre or middle.** Every other draggable thing in the preview settles onto the centre lines with an amber guide; caption segments were the one exception, so a caption could only be eyeballed onto centre and would sit a fraction of a percent off. `captionDragGeometry`'s `move` branch was a pure translate with no snap at all. The omission came from the (correct) observation that `useDragOverlay`'s **edge** snap does not transfer — its `edgeX = (0.5 - s/2) * 100` geometry assumes an `inset-0` box scaled from its centre, whereas a caption's `scale` multiplies a small content-sized anchor box, so the same formula would compute snap positions that mean nothing — but the **centre** snap is geometry-independent: `offsetX: 0` is the frame's horizontal centre and `offsetY: 0` its vertical middle for a caption exactly as for an overlay. Centre/middle snap is restored with `CAPTION_SNAP_THRESHOLD` pinned to the same 2.5%-of-frame radius `useDragOverlay` uses (a test asserts the boundary from both sides so the two gestures cannot drift apart), the snapped value is what gets committed rather than the raw pointer position, and `CaptionPreview` now draws the same amber centre/middle hairlines under the same `drag.type === 'move'` gate the overlay layer uses. Edge snap remains deliberately unimplemented for captions, and resize gestures stay unsnapped and never move the segment. (`montaj_assets/editor/src/video/preview/captionDragState.ts`, `montaj_assets/editor/src/video/preview/CaptionPreview.tsx`, `montaj_assets/editor/src/video/__tests__/captionSnap.test.ts`)

## v3.9.0

- **Captions: per-segment positioning.** `CaptionSegment` gains optional `offsetX`/`offsetY` (percent of frame, matching the convention overlay and video items already use — `offsetX: 22` means 22% of frame width, not `0.22`) and `scale` (visual scale of the whole caption block about its own centre — a CSS transform, so it scales `subtitle`'s background box and `outline`'s text stroke too and does not re-wrap the text; default 1). Previously every segment rendered wherever its style template hardcoded it (`bottom: 18%`, or `10%`/`8%` for `clean`/`subtitle`) — a beat that puts a whiteboard explainer card, lower-third, or screenshot at the bottom of frame had no way to keep captions clear of it short of deleting them for that stretch. All seven caption templates now route through a shared two-box positioner (new `montaj_assets/overlay-runtime/position.js`, `captionOuterStyle`/`captionInnerStyle`): a frame-sized outer box carries `translate(ox%, oy%)` so the percentages resolve against the frame rather than the text, and an inner box keeps the template's historical anchor and scales about its own centre, so a bottom-anchored caption grows in place instead of drifting toward frame centre. A segment with no positioning falls back to that historical anchor unchanged; a per-template equivalence test compiles all seven templates through the same esbuild path the real render uses and asserts every wrapper (both branches of `karaoke`, `outline`, and `highlight-box`) against its historical style at zero offset, including that the outer box carries no `transform` key at all — an identity `translate(0%, 0%)` would still create a containing block and stacking context, so only the key's absence preserves today's rendering. The positioner is re-exported through `montaj_assets/render/core/index.js` and `overlay-runtime`'s `makeOverlayGlobals()` rather than imported directly by the templates — the editor preview's `overlay-eval.ts` strips every import line from template source and injects only a fixed global whitelist, so a direct sibling import would have rendered fine on the Puppeteer path while throwing `ReferenceError` in the editor preview, the same mechanism `interpolate`/`spring` already use. Positioning is only honored by the JSX/Puppeteer render path — the older ffmpeg `drawtext` branch can't place segments individually and keeps honouring only the track-level `position` field, which is now called out in `docs/schemas/project.md`. (`montaj_assets/render/templates/captions/*.jsx`, `montaj_assets/overlay-runtime/position.js`, `montaj_assets/overlay-runtime/index.js`, `montaj_assets/render/core/index.js`, `montaj_assets/editor/src/schema.ts`, `montaj_assets/render/test/caption-position.test.mjs`)
- **Editor: caption segments are now a real timeline row, selectable and draggable like any other item.** New `CaptionTrackRow` gives the caption track one block per segment in the timeline — click to select, double-click to edit text, drag an edge to retime — with an empty state when the project has no captions. Selecting a segment, either from that row or by clicking its box in the preview, shows a drag/resize box on the preview canvas, the same affordance overlays already have; the caption layer itself stays non-interactive (its DOM is template-specific and reshapes every frame, e.g. `word-by-word` swapping content), so the box is a separately measured hit target over the rendered text. Dragging the box moves the segment (`offsetX`/`offsetY`); dragging a corner resizes it (`scale`). (`montaj_assets/editor/src/video/timeline/CaptionTrackRow.tsx`, `montaj_assets/editor/src/video/preview/CaptionPreview.tsx`, `montaj_assets/editor/src/video/preview/captionDragState.ts`, `montaj_assets/editor/src/video/timeline/makeCaptionEdit.ts`, `montaj_assets/editor/src/video/VideoEditor.tsx`, `montaj_assets/editor/src/video/timeline/Timeline.tsx`)
- **Fixed: regenerating captions mid-session could leave every segment unselectable.** Caption segments are generated without `id`s (`steps/lyrics/caption.py`); the editor backfills a `cap-<n>` id for any that's missing one, but the backfill effect was keyed on `project.id` alone. Regenerating captions replaces `project.captions` without changing `project.id`, so it produced a fresh batch of id-less segments the effect never re-ran for. The effect now also re-fires on `project.captions`, and the mint is collision-proof against a segment that already carries a literal `cap-N` id. (`montaj_assets/editor/src/video/VideoEditor.tsx`)
- **Fixed: editing a transcript segment's text cost two undo steps and two saves.** `makeCaptionEdit` fires both of its optional callbacks with the same updated project, and `TranscriptPanel`/`TranscriptModal` passed both — each wired in `VideoEditor` to `sync.mutate`, which pushes an undo entry and enqueues a save on every call. One text edit therefore pushed two identical undo entries (so a single Undo appeared to do nothing) and queued the same save twice. Both call sites now pass only `onCaptionEdit`, the file's own commit channel — `onProjectChange` remains the live-preview channel the fontsize slider and colour swatches use, and `EditableSegment` only fires on blur when the text actually changed, so there was never a live-preview gesture to preserve here. `TranscriptModal` had no other use for the prop, so it was dropped from that component entirely (neither component is re-exported from the package index, so this is not a public API change). (`montaj_assets/editor/src/video/timeline/TranscriptPanel.tsx`, `montaj_assets/editor/src/video/timeline/TranscriptModal.tsx`, `montaj_assets/editor/src/video/timeline/Timeline.tsx`)
- **Fixed: regenerated captions skipped word-timing repair, and the repair could not converge on irregular whitespace.** `repairCaptionWords` rebuilds a segment's per-word timings when its `words` array disagrees with its `text`, but the effect that runs it was keyed on `project.id` alone — the same blind spot as the id backfill above — so a mid-session caption regeneration never got repaired. Widening the dependency exposed a latent non-convergence: `repairSegment` compared `words.join(' ')` (always single-spaced) against a merely trimmed `seg.text`, so any segment whose text contained a double space, tab, or newline between words compared unequal forever — it would be "repaired" on every pass, each time producing a same-content but referentially-new `words` array, and with the widened dependency that would have become an unbounded `applyExternal` loop. The comparison now collapses internal whitespace on both sides, which also stops a purely cosmetic whitespace difference from needlessly discarding real per-word timings. (`montaj_assets/editor/src/video/captionRepair.ts`, `montaj_assets/editor/src/video/VideoEditor.tsx`)

## v3.8.0

### Performance
- **Serve** — project lookups use a validated in-memory index instead of re-scanning the whole workspace per request; file streaming moved to `FileResponse` (native range requests, reads off the event loop).
- **Render** — timeline segments encode in parallel (default 2 workers, `MONTAJ_SEGMENT_WORKERS` to tune); audio-presence probed once per source instead of once per segment.
- **Overlays** — `spring()` memoizes its integration steps (identical output, no more per-frame re-simulation).
- **MCP** — tool calls no longer block the server's event loop; concurrent requests are serviced during long renders.
- **Editor** — playhead time moved to a subscription store: playback no longer re-renders the whole editor 60×/s; timeline derived state memoized; custom-overlay props no longer deep-cloned per frame.
- **UI** — routes are code-split; three.js/ReactFlow load only on pages that use them.
- **CLI** — `mtj <command>` imports only that command's module (faster startup).

## v3.5.3

- **Render: the timeline origin is floored at t=0, so a clip/overlay with a negative `start` no longer shifts the whole video and leaves a black head gap.** An item may carry a negative `start` — the interactive editor clamps drags/trims to `>=0`, but a programmatic author can persist `start < 0` (e.g. the overlays workflow placing a full-source background reel at `-firstClipInPoint` to stay aligned to source time). The segment planner seeded its first boundary at the earliest item start with no zero-floor, so a negative value became the timeline origin: the entire output shifted later by `|minStart|`, tracks correctly anchored at 0 (the source clips) rendered **black for `|minStart|` seconds** while the negative-start overlay filled from frame 0, and the render disagreed with the editor preview (which already treats `t<0` as `t=0`). `planSegments` now floors every boundary at 0 (`Math.max(0, quantize(t))`); `encode-segment`'s existing `max(0, segStart - start)` seek then advances each item into its pre-0 portion, matching the preview's `playhead - start` convention. Items entirely before 0 collapse to a single 0 boundary and produce no segment. Repro: `2026-06-26-cruces-objetivo-ultimo-dia` (reel overlay at `start=-0.335` → 0.335s black top, render 32.3s vs timeline 31.98s). (`montaj_assets/render/segment-plan.js`, `montaj_assets/render/test/segment-plan.test.mjs`)
- **Normalize caches are written atomically, so an interrupted or concurrent normalize can never poison the cache and crash later renders.** The `*_normalized_<colorspace>.mp4` cache used to be written by ffmpeg straight to its final path. A normalize killed mid-encode (the 600s timeout firing, the render cancelled, the machine sleeping, an OOM) — or two renders of the same project normalizing the same source at once — left a half-written / byte-interleaved file *at the cache path*, which later renders then fed to ffmpeg and died on (`Invalid NAL unit size`, `missing picture in access unit`, AAC `Reserved bit set` / `Number of bands exceeds limit`). `normalize()` and `normalize_window()` now encode to a per-pid `…tmp.<pid>.mp4` sibling and `os.replace()` it onto the cache only on a clean exit, mirroring the existing `lib/normalize_image.py` pattern: a failed/killed/timed-out run leaves at most an orphaned temp (the cache stays the previous good file or absent), and concurrent encoders serialize on the atomic rename instead of interleaving bytes. Stale temps are swept on entry, liveness-checked so a live sibling's in-progress temp is never reaped. (`lib/normalize.py`, `tests/test_normalize.py`)
- **Render modal shows the full streaming log on montaj-native again; Hub clients keep the phase stepper.** The render overlay's progress UI is now a host-chosen flag, threaded down exactly like `assetsPlacement`: a new `VideoEditorProps.renderProgressView?: 'phases' | 'logs'` (default `'phases'`) flows VideoEditor → ReviewSurface → `RenderModal`'s `progressView`. The montaj-native desktop host passes `'logs'` and gets the scrolling render-log panel (colorized lines + Copy button) back; Hub clients (Los Parceros) omit it / pass `'phases'` and keep the compact Preparing → Rendering → … → Saving stepper. The SSE render path now accumulates log lines again (required for the log panel) instead of only nudging the stepper to "rendering"; `'logs'` only renders content on the SSE `adapter.render()` transport. - **Render: a render survives a dropped client connection instead of being killed mid-flight.** A manual render streamed its log over SSE and was tied to that request: on `request.is_disconnected()` it called `kill_tree()`. But a multi-minute render (e.g. 16 Puppeteer overlay segments) streamed through the Hub proxy + Cloudflare tunnel outlives the tunnel's ~100s wall — the tunnel cuts the long-lived stream, the sidecar saw the disconnect, and **killed the render before it produced any output** (it stalled at whatever segment it had reached, with `/outputs` empty). - **Rich-text formatting toolbar** — selected text elements now expose a floating toolbar with bold, italic, uppercase/lowercase/capitalize case-cycle, left/center/right/justify alignment, font-family picker, font-size stepper, and a color swatch. Formatting writes back via `updateOverlayProp` so every change is immediately reflected in the preview and persisted to `project.json`.
- **Double-click inline text editing** — double-clicking any text element on the canvas opens an in-place `contenteditable` editor. Enter commits the edit, Shift+Enter inserts a newline, Escape cancels (restores the prior value), and clicking outside the element commits.
- **Undo / redo with keyboard shortcuts** — the editor now maintains a snapshot history. Cmd/Ctrl+Z steps back, Cmd/Ctrl+Shift+Z or Cmd/Ctrl+Y steps forward. Undo/Redo buttons in the toolbar reflect availability.
- **Non-destructive 8-handle image cropping** — selecting an image element and entering crop mode via the panel reveals eight edge and corner handles. Dragging any handle adjusts the visible crop rectangle; confirming (Enter or clicking outside) writes the crop fractions to `project.json`. Cropping is disabled when the element is rotated. Applying a crop also updates the element's bounding box (crop-also-resizes), so the layout reflects the visible area.
- **`mediaId` passthrough on image elements** — image overlay items may now carry an optional `mediaId` field (for host-side media tracking) that round-trips through the schema without affecting render behavior.
- **Element visibility toggle** — the property panel now shows an eye toggle for the selected element. Hidden ids are passed in via the new `hiddenElementIds` prop and omitted from the interactive canvas only (editor-only, never persisted); the host owns the hidden-set and flips it via the `onToggleElementVisibility` callback. Lets you temporarily hide a scrim/background to position overlays beneath it.
- **`onSelectionChange` callback + `toolbarActions` slot** — `<CarouselEditor>` now reports the selected element (or `null`) via `onSelectionChange`, and renders the host-injected `slots.toolbarActions` in the canvas toolbar (previously declared but unrendered). Together these let a host drive selection-aware chrome (e.g. a "regenerate image" action targeting the current selection).

### Carousel rendering

- **Carousel slides now export at 2× by default.** The carousel renderer's `--scale` default flips from `1` to `2`, so omitting the flag rasterizes each slide at 2× device pixels (e.g. portrait 1080×1350 → 2160×2700 PNGs) — crisp on desktop/Retina out of the box. The default lives in one place: a `DEFAULT_SCALE` constant in `render-carousel.js`. Both upper layers (`montaj render` and `POST /projects/{id}/render`) pass `--scale` only when explicitly set, so they inherit the renderer's default — meaning the auto-render that fires when a project reaches `status: final` also produces 2× output with no other changes. Only Puppeteer's `deviceScaleFactor` changes: the logical viewport stays at the design canvas and overlay coordinates / `project.settings.resolution` are untouched, so layout is pixel-identical to 1× — just rasterized at 2×. Pass `--scale 1` (or `?scale=1`) for the previous design-resolution output; `--scale 3` still works. The video render path (`render.js` / `renderer.js`) is unaffected — it never used this flag. Manifest fields (`scale`, `outputResolution`, per-slide `width`/`height`) reflect the active scale as before.

### Video editor

- **Full timeline-based video editor** — documented here for the 3.0.0 milestone; the editor accreted across the 2.x line (unified `tracks` in v2.0.0, multi-select in v2.5.7, render-pipeline fixes through v2.6.x) and never had a consolidated changelog entry. The browser editor opens any `format: 'video'` / `project_type: 'editing'` project on a multi-track timeline built on the unified `tracks` array: `tracks[0]` is the primary footage track; `tracks[1+]` hold overlay (JSX), image, and video items, alongside audio lanes. Clip editing is non-destructive over trim specs — **cut**, **split-at-playhead**, and edge-**resize** run through the cut engine (`applyCutToTracks`, `splitAtTime`, `collapseGaps`), with an optional **ripple ("magnet") mode** that closes gaps on delete/cut. Clips, overlays, and audio support cross-track **multi-select** (shift / cmd-click) with ripple-aware delete, uniform mute, and relative-delta resize; drag/resize tracks the cursor 1:1 at any zoom, and the timeline renders per-clip **waveforms** (chunked PNGs via the `waveform_image` step) with cursor-pivoted zoom. A **preview player** scrubs the assembled timeline, compositing JSX overlays live — with file-watch hot-reload and an error boundary so a broken overlay never blanks the editor — over the footage. **Captions** are a data track (not pixels), authored from the transcript in `word-by-word` / `karaoke` / `pop` / `subtitle` styles and rendered at preview and final-render time. **Version history** lists the project's git snapshots (auto-committed on every `pending → draft → final` transition) with one-click restore. **Render** streams ffmpeg/compose progress over SSE into a modal and produces a frame-quantized MP4 (plus a `.zip` of outputs). The surface is driven by the agent-first editing pipeline — the `clean_cut`, `overlays`, `explainer`, `floating_head`, `short_captions`, and `lyrics_video` workflows trim/clean/transcribe/select-takes/remove-fillers and author overlays, advancing the project `pending → draft` for human review and `→ final` on approval. Mobile surfaces are view-only (preview + render).
- **Video editor extracted into `@bycrux/editor` package** as `<VideoEditor>` — mirrors the Phase 2a carousel extraction. The package now ships both assembled editors. Moved into the package boundary: the timeline (track rows, waveform display, clip selection), `<PreviewPlayer>` and `<CarouselPreview>`, the cut engine (`applyCutToTracks`, `splitAtTime`, `collapseGaps`), version history panel, and render modal. Montaj's UI consumes the package via the same `file:../editor` link (dogfood) with no user-visible behavior change. New optional adapter methods added to `EditorAdapter`: `listVersionHistory` / `restoreVersion` (version history), `getWaveformChunks` (timeline waveform), `clearOverlayCache` (live overlay reload), and `resolveCaptionTemplate` (caption style). Montaj-pipeline-specific UI — clip inspect modal, subcut/regen tool, run history panel, rerun button, storyboard integration, page header, and mobile layout — stays in the Montaj host via render-props / slot overrides; the package boundary holds zero `@/` alias imports and no references to Montaj-internal types (`RegenQueueEntry`, `RunSnapshot`, `projectType`).

### Editor architecture

- **Host-agnostic `editor-core` module** (`montaj_assets/ui/src/editor-core/`) — all state management (project reducer, undo/redo snapshots), gesture handling (drag, resize, rotate, crop), text editing, formatting toolbar, and the overlay preview live in a host-agnostic boundary. Future client apps consume `editor-core` by supplying an `EditorAdapter` (for persistence and SSE hooks) and an optional theme/slots override, with no coupling to Montaj internals.
- **`EditorAdapter` + optimistic mutation queue** — mutations are applied to local state immediately and enqueued for the host via the injected adapter. SSE events from the server are deferred while a mutation is in-flight and replayed once the queue drains, preventing server echo from clobbering in-progress edits.
- **Carousel editor extracted into `@bycrux/editor` package** (`montaj_assets/editor/`) — the editor-core boundary is now a standalone, publish-ready npm package (ships raw TypeScript source, no build step required by the consumer). It owns the editor-facing schema (`EditorProject` and all overlay/element types), the full `EditorAdapter<P>` generic contract, all state/gesture/text/preview pieces, the assembled `<CarouselEditor>` component, and vendored UI primitives. Montaj's UI consumes the package via a `file:../editor` link (dogfood) with no user-visible behavior change; Montaj's own pipeline and agent types remain in the UI package. The package boundary is enforced: `montaj_assets/ui` holds no `@/editor-core` imports and the editor package holds no `@/` alias imports. Video editor and mel-hub adoption are follow-up work. The package is publish-ready but not yet published to npm.

### Dependencies

- **React 19** — upgraded `@xyflow/react` (ReactFlow) from v11 to v12 and `@react-three/fiber` from v8 to v9, both of which require React 19. All three consumers of `montaj-overlay-runtime` were moved to React 19 in lockstep — the UI (`montaj_assets/ui`), the runtime package itself, and the render engine (`montaj_assets/render`) — because the shared runtime's r3f-v9 globals only bind under React 19; leaving the render engine on React 18 broke `window.__setFrame` initialization for every overlay bundle (2D and 3D alike). No user-visible behavior change in the workflow-builder (NodeGraph) or overlay rendering/preview; the upgrade resolves a peer-dependency conflict that blocked further library updates.

## v2.7.0

### Added
- Per-request credential passthrough for `POST /api/steps/:name`. A reserved top-level `credentials` field in the step request body — shaped `{provider: {key: value, ...}, ...}` — is validated against the `KNOWN_PROVIDERS` allowlist in `lib/credentials.py` (`build_env_overlay`) and, on success, injected as environment variables into that single step subprocess only. The field is popped from the body before param validation and CLI-arg construction ever see it, so it can never collide with a schema param, leak into argv, or be echoed back in a validation error; the server's own environment (`os.environ`) is never mutated. Unknown providers, unexpected keys, and non-string/empty values are rejected with a 422 `invalid_credentials` before the subprocess is ever spawned, with value-free error messages (CredentialError messages name the offending provider/key but never a value). The primary use case is keyless multi-tenant serve deployments: the Hub (or any caller) passes the tenant's credential at call time rather than pre-configuring a per-tenant credentials file on the Montaj server. Local `montaj credentials`-file behavior is completely unchanged — when no `credentials` field is present the step subprocess inherits the server's environment exactly as before. Step error responses are additionally scrubbed of injected passthrough values — if an upstream provider echoes the caller's key in its error body (OpenAI does), the value is replaced with `[redacted]` before the 500 detail leaves the server; ambient/local credentials are untouched by the scrubber.
- New step `search_images` — searches for licensed images on Wikimedia Commons or TheSportsDB and prints a JSON object `{"results": [...]}` to stdout. Each result carries: `title`, `url`, `width`, `height`, `mime`, `license`, `artist`, and `source` (`"commons"` or `"sportsdb"`). Params: `query` (required), `provider` (enum `commons|sportsdb`, default `commons`), `limit` (int, default 10, max 30). The Commons provider uses the MediaWiki API (`generator=search` with `gsrnamespace=6` for the File namespace, `prop=imageinfo` with `iiprop=url|size|mime|extmetadata`); license and artist come from the `LicenseShortName`/`Artist` extmetadata fields, with HTML tags stripped from the artist string, and non-image MIME types and SVGs are filtered out. The SportsDB provider queries `searchteams.php` and returns badge URLs for Soccer entries only (`license: "editorial"`, `mime: "image/png"`). The step is stateless (no disk writes); failures surface as `bad_provider` / `search_failed` structured errors. Backed by `steps/media/search_images.py` with shared logic in `lib/image_sources.py`.
- New step `fetch_image` — downloads an HTTPS image URL to a caller-supplied `--out` path, with SSRF and content-type guards. Pre-flight (before opening any connection): the URL must be HTTPS; the hostname must be on the image allowlist (`DEFAULT_IMAGE_HOSTS` — `upload.wikimedia.org`, `commons.wikimedia.org`, `www.thesportsdb.com`, `r2.thesportsdb.com` — merged with the comma-separated `MONTAJ_HTTP_ALLOWED_HOSTS` env var); and the hostname must resolve to publicly routable IPs only (every `getaddrinfo` result is checked with `ipaddress.ip_address(...).is_global`, rejecting RFC 1918 / loopback / link-local / reserved addresses; resolution failure also rejects). Violations fail with `url_rejected`. HTTP redirects are not followed — a redirect response fails with `redirect_rejected`, since following one to a private host would bypass the pre-connection checks. The response `Content-Type` must start with `image/` (else `not_an_image`), and the download is streamed with a running size cap (`--max-bytes`, default 26214400 = 25 MiB) — exceeding it deletes the partial file and fails with `too_large`. On success the step prints the absolute output path (output type `image`). Parent directories of `--out` are created on demand. Backed by `steps/media/fetch_image.py` with the fetch logic in `lib/image_sources.py::fetch_image_to_path`. The allowlist is intentionally narrow by default and operator-extendable: deployments that need additional image CDNs add their hostnames to `MONTAJ_HTTP_ALLOWED_HOSTS` without any code change.

- Image track items support an optional `fit` field (`'cover' | 'contain' | 'fill'`, default `'cover'`) controlling how the source image fills its `scale`-derived box. `cover` preserves aspect ratio and fills the frame, cropping overflow; `contain` preserves aspect ratio and letterboxes (with a transparent pad, so an image on an upper track no longer blacks out lower tracks); `fill` is the legacy non-AR-preserving stretch, retained for explicit opt-in. Schema: `VisualItem.fit` in `montaj_assets/ui/src/lib/types/schema.ts`. Editor: a compact Cover/Contain/Fill segmented control (`FitControl` in `montaj_assets/ui/src/components/preview/OverlayItemsLayer.tsx`) appears under a selected image item and commits through the existing `onOverlayChange` path (`useDragOverlay`, `PreviewPlayer`, `ReviewView.handleOverlayChange` all widened to carry `fit`). No Python-side change needed — `engine/validate.py` checks required fields only, not a key whitelist, so the new field passes validation on existing projects.

## v2.6.2

### Fixed
- `montaj credentials` STILL echoed `^M` after Enter on the provider-selection prompt for the same users the v2.6.1 fix was supposed to help — confirming the v2.6.1 diagnosis was wrong. The v2.6.1 entry blamed ANSI escape codes in the prompt string confusing GNU readline's column tracking and "fixed" it by writing the prompt directly to stdout and passing an empty string to `input()`. That fix landed on the Homebrew install, ran on the same affected users' machines, and made no difference. Actual root cause, found by `import readline; print(readline.__doc__)` on the Homebrew install: Homebrew's `python@3.12` (the install path montaj ships through) is compiled against **libedit**, not GNU readline. The `readline` stdlib module on this build returns *"Importing this module enables command line editing using libedit readline"*. libedit is BSD's editline library, the same one Apple's system Python uses; it ignores GNU readline's `\001`/`\002` zero-width prompt markers entirely, which is why the prior fix's premise — that the line-editor was over-counting visible prompt width — was a non-issue on this build in the first place. The actual issue is that libedit, like any line editor, preps the tty for arrow-key escape-sequence reads before each `input()` call by toggling input flags via `tcsetattr` (typically clearing `ICANON` and adjusting `VMIN`/`VTIME`, sometimes clearing `ICRNL`). On terminal+pty combos where the user's Enter keystroke gets echoed as a bare CR rather than being post-processed back to CRLF (some tmux configs without `default-terminal "screen-256color"`, IDE-embedded terminals in certain modes, Windows Terminal over SSH, fresh ttys without proper `ONLCR` setup, mosh in some configurations), the tty driver's `ECHOCTL` flag then displays the bare CR as the literal text `^M`. macOS Terminal.app, iTerm2, and gnome-terminal mask the issue with their default pty configurations, which is the "some users" pattern. Actual fix replaces `input()` with `sys.stdin.readline().rstrip("\r\n").strip()` at `cli/commands/credentials.py:120` (the provider-selection prompt). `sys.stdin.readline()` is a plain stdio read that bypasses `PyOS_Readline` entirely — libedit is never invoked for this prompt, the tty stays in its caller-configured mode, and there is no line-editor terminal prepping to misconfigure CR echo. The trade is the loss of arrow-key editing and history for this one prompt, which is fine for a number selector. The `_read_secret` fallback `input()` at line 247 is left untouched: it only fires when `getpass.getpass()` raises `EOFError`/`OSError` (i.e. non-tty environments), where libedit isn't engaged anyway. The primary `getpass.getpass(prompt)` call is also untouched because it uses its own raw tty loop (open `/dev/tty`, disable `ECHO` via `tcsetattr`, plain `os.read`), bypassing `PyOS_Readline` and libedit entirely. The misleading "ANSI in prompt" comment block introduced by the v2.6.1 attempt is replaced with a comment that names the actual cause (libedit terminal-prep + `^M` echo) and explicitly notes the prior wrong attempt for future-reader clarity. All 11 `tests/test_credentials.py` tests continue to pass; no new tests added because the bug is at the libedit/tty driver boundary and isn't observable in a non-TTY test harness.

## v2.6.1

### Fixed
- `montaj credentials` echoed a literal `^M` character after the user typed a number and pressed Enter at the provider-selection prompt, on certain terminal + Python combos (some tmux configs, IDE-embedded terminals, Windows Terminal over SSH). Root cause was raw ANSI escape codes embedded in the prompt string passed to `input()` in `cli/commands/credentials.py::handle` (`input(f"  Which provider? {_dim('(...)')}: ")`). Python's `input()` routes the prompt through `PyOS_Readline`, which on most builds hands the string to GNU readline (Linux, Homebrew Python on macOS) or libedit (macOS system Python) so the user can arrow-key edit and use history. The line-editor library tracks the cursor's visible column by counting the prompt's character width — but it counts the raw bytes of the ANSI escape codes (`\033[2m`, `\033[0m`) as visible characters, even though they render as zero width on screen. GNU readline exposes `RL_PROMPT_START_IGNORE`/`END_IGNORE` (`\001`/`\002`) markers to mark zero-width regions, but the credentials code didn't use them; libedit doesn't support those markers at all. With the column miscounted, the line-editor emits a bare `\r` when the user presses Enter to "return to column 0 before printing the newline." On terminals where the `ONLCR` output flag isn't translating that lone CR back to CRLF (some tmux configs without `default-terminal "screen-256color"`, VSCode integrated terminal in certain modes, Windows Terminal over SSH, mosh in some configurations), the bare CR echoes literally as `^M`. macOS Terminal.app, iTerm2, and gnome-terminal masked the issue with their pty defaults, which is why the bug wasn't visible to all users. Fix writes the colored prompt directly to `sys.stdout` first and then calls `input()` with an empty prompt, so the line-editor library sees a zero-width prompt and its column tracking is correct regardless of any ANSI bytes that preceded the input call. The `_read_secret` fallback path at `cli/commands/credentials.py:224-226` already followed this pattern; only the provider-selection prompt at line 103 had the leak. The primary `getpass.getpass(prompt)` call in `_read_secret` is unaffected by this bug because `getpass` on Unix uses its own raw tty loop (write prompt, disable ECHO, read line directly from `/dev/tty`) rather than `PyOS_Readline`, so ANSI in its prompt doesn't trigger column-tracking miscounts. All 11 `tests/test_credentials.py` tests continue to pass; no new tests added because the bug is at the terminal-emulator/readline boundary and isn't observable in a non-TTY test harness.

- Final-rendered MP4s could show a short black frame at certain clip transitions even though the editor's preview rendered the clips continuously. Specifically: any clip boundary whose quantized frame index landed exactly one frame after another item's quantized boundary (e.g. an overlay end at `4.75s` → quantized `143/30 = 4.7667s`, followed by a clip-cut at `4.8061s` → quantized `144/30 = 4.8s`) caused a ~200 ms black gap because the clip boundary at `4.8` was silently dropped. Root cause was a floating-point cancellation bug in the proximity-snap pass in `montaj_assets/render/segment-plan.js::planSegments`, which was kept "as defense in depth" after the v2.6.0 quantize fix landed: `if ((sorted[i] - snapped[last]) < frameDur) collapse`. For two adjacent grid points the mathematical gap is exactly `1/fps`, but IEEE 754 subtraction can return a value `~1e-16` below `1/fps` — `144/30 - 143/30` in double-precision evaluates to `0.033333333333333215`, while `1/30` evaluates to `0.03333333333333333` — so the `gap < frameDur` test misread "exactly one frame apart" as "duplicates, collapse them" and silently dropped the second boundary. The collapsed segment `[4.7667, 5.0]` then failed the active-items filter on both adjacent clips: clip-1's raw end (`4.8061`) didn't satisfy `>= end - frameDur` (= `4.967`), and clip-2's raw start (`4.8061`) didn't satisfy `<= start + frameDur` (= `4.8`). With no items active, the encoder rendered black canvas for the segment's duration. The editor preview never showed this because it draws directly from `tracks[0]` raw timestamps and doesn't run `planSegments`. Fix replaces the float-gap comparison with an integer frame-index comparison: `Math.round(a * fps) === Math.round(b * fps)` is cancellation-proof and semantically identical for the "within ~1 frame" case the snap is supposed to catch. Regression coverage added: `test/segment-plan.test.mjs` reproduces the exact failing configuration from the original bug report (clip boundary at `4.8061s` + overlay end at `4.75s`, with `ov-term1` starting at `5.0s` after a `4.75s → 5.0s` gap) and asserts (a) no segment in the resulting plan has empty items, (b) the segment starting at `143/30` exists and contains clip-1, (c) the segment starting at `144/30` exists and contains clip-2. Verified end-to-end on the project that triggered the bug: pre-fix the planner emitted seg4 `[4.7667, 5.0]` with `items=[]` (black 7 frames in the render); post-fix the planner correctly emits seg4 `[4.7667, 4.8]` with clip-1 + ov-url and seg5 `[4.8, 5.0]` with clip-2. All 67 render-asset tests pass.

### Fixed
- Audible "mic pops" at every intra-clip overlay start/end boundary in the final-rendered MP4 — distinct from a normal scene cut, present even after the visual sub-frame quantization fix landed, loud enough on speakers to be obvious. Diagnosed by probing consecutive-sample deltas in the rendered PCM around four representative boundaries in a 4K HDR project: intra-clip seams (where the audio should be perfectly continuous because both sides come from the same clip recording) produced max deltas of 1666–2356, while the natural inter-clip cut produced only 1382 — i.e. the per-segment audio handoff was louder than an actual scene cut. Root cause was the audio stream-copy fast path in `montaj_assets/render/encode-segment.js::encodeSegment` Step 5 (the `audioLabels.length === 1 && streamCopyCandidates.length === 1` branch). For every segment containing exactly one unmuted video item sourced from an `_audioclean.mp4` file with `volume=1` — which is almost every intra-clip segment, since track 0 never overlaps with itself — ffmpeg was invoked with `-ss <segStart> -t <duration> -i <_audioclean.mp4> -c:a copy`: the demuxer seeked to the nearest AAC frame at-or-before `<segStart>` (AAC frames at 48 kHz are 1024 samples = 21.3 ms, so the seek landed up to ~21 ms early), stream-copied the AAC packets into the per-segment MP4, and wrote an `edts/elst` edit list marking the pre-seek samples as "skip on playback." The `-f concat` demuxer in `compose.js::compose` then re-encoded audio at concat with `-c:a aac` — but the concat demuxer is known to drop per-input MP4 edit lists when audio is being transcoded ([ffmpeg ticket #2330](https://trac.ffmpeg.org/ticket/2330), [#7426](https://trac.ffmpeg.org/ticket/7426)), so the pre-seek (and post-end) samples from each segment's first AAC frame were decoded as real audio. The result was 10–25 ms of duplicated waveform at every intra-clip seam, which re-encoded into an audible click in the final AAC track. Inter-clip cuts (e.g. clip-2 → clip-3) popped less because the "duplicated" samples there are tail-of-clip-A overlaid on head-of-clip-B — two unrelated recordings whose combined energy is no worse than the cut itself; intra-clip seams popped worst because the duplicated samples are real voiceover overlapping itself. Fix replaces per-segment AAC entirely with PCM s16le: the stream-copy fast path and the `streamCopyCandidates` collection that fed it are deleted; the non-stream-copy encoder branch — previously `-c:a aac_at -b:a 192k -ar 48000 -ac 2` — is now `-c:a pcm_s16le -ar 48000 -ac 2`, with `atrim=0:${duration}` added to the per-item audio filter (before `asetpts=PTS-STARTPTS`) to make sample-exact duration trimming explicit in the filter chain rather than implicit in ffmpeg's `-accurate_seek` + `-t` defaults. PCM has no framing, no encoder priming, and no edit-list metadata, so per-segment encoder/container artifacts disappear at concat; an off-pipeline reproduction on a controlled AAC source measured the residual seam delta dropping from ~2400 (pre-fix) to ~500–800 (post-fix), with the residual coming from the AAC decoder's per-process seek precision rather than the priming/edit-list bug. The final `-c:a aac` pass in `compose.js` then re-encodes the joined PCM stream to AAC once at end-of-pipeline — exactly as before from the user's perspective (final output is still AAC 192 kbps), but now from a continuous-enough waveform instead of stitched encodes. The previous `aac_at`-under-libx265-4K-concurrent-encode AAC-bitstream corruption concern (which the deleted stream-copy fast path was originally introduced to work around) is also resolved in principle by this change: `aac_at` is no longer called at all, and the only AAC encode in the pipeline (the concat re-encode in `compose.js`) runs after every libx265 segment process has exited. Trade: per-segment temp files grow ~8× on audio (~370 KB more per segment; ~12 MB extra temp disk during a typical 30-segment render), cleaned up at end of compose unless `MONTAJ_KEEP_SEGMENTS` is set. PCM s16le in MP4 is muxed as `codec_tag=ipcm` (ISOBMFF integer PCM) and reads back as `pcm_s16le` via ffprobe — `compose.js`'s concat command (`-c:v copy -c:a aac`) decodes it cleanly without modification. Regression coverage added: five tests in `test/encode-segment.test.mjs` assert (1) single-source segment audio codec is `pcm_s16le` and `aac_at` no longer appears as an arg, (2) the `anullsrc` silent path emits `pcm_s16le`, not `aac`, (3) the multi-source amix path emits `pcm_s16le`, (4) per-item audio filter includes `atrim=0:${duration}` with `atrim` preceding `asetpts=PTS-STARTPTS` (locked against a fractional `22/30` duration of the kind the frame-aligned planner emits), (5) a segment with the previously-fast-path signature (single `_audioclean.mp4` source, `volume=1`) now routes through the encoder filter+PCM path with `-c:a pcm_s16le`. All 66 render-asset tests (segment-plan + encode-segment + render-helpers + sample-frame + renderer-image-interception + render-carousel) pass.

- Final-rendered MP4s flickered and popped at every overlay start/end and clip transition — a sub-frame freeze visible as a brief judder, plus an audible click in some cases. Root cause was sub-frame timing leakage through the segment planner. Project boundaries arrive as float seconds from the editor (e.g. `1.875`, `4.7177`, `8.9474`, `12.951`), and most are NOT integer multiples of `1/fps` — at 30 fps, `4.7177 × 30 = 141.53`, off by half a frame. `montaj_assets/render/segment-plan.js::planSegments` collected those raw floats into the boundary set, applied only a "snap pairs within one frame to the same value" pass (intended to kill degenerate micro-segments, not to grid-align), and then handed `{start, end}` pairs straight to `encodeSegment` whose `duration = end - start` likewise wasn't a multiple of `1/fps`. The libx265 encoder, told `-t 2.843`, produced 85 frames @ 30fps (2.833 s of pts span) but MP4 recorded 2.843 s of *track duration* — the trailing ~10 ms hung off the last frame. Stream-copy concat (`compose.js`, `-c:v copy`) preserved that per-segment slack: ffprobe on the rendered output showed consecutive frames spaced 0.044 s apart at boundaries (1.33 × a frame) instead of the uniform 0.033 s seen elsewhere. The viewer perceives this as a sub-frame freeze at the previous frame, then a sharp snap to the next — i.e. the "pop" at overlay transitions. Cumulatively, a 62 s render with 30 sub-frame boundaries came out 0.34 s longer than the project's nominal duration (final `avg_frame_rate = 29.815` instead of `30.000`). Fix: `planSegments` now quantizes every boundary to the frame grid (`Math.round(t * fps) / fps`) **before** the proximity-snap pass, so every segment duration is an exact multiple of `1/fps`, the encoder produces an integer frame count whose pts span equals the declared duration, and concat boundaries have uniform `1/fps` gaps. `collectPuppeteerSegments` (in `render.js`) applies the same quantization to each overlay's `startSeconds`/`endSeconds`/`frameCount` so the Puppeteer-rendered overlay aligns frame-for-frame with the segment that displays it — previously, `frameCount` used `Math.ceil(...)` on the raw float and could overshoot the segment by one trailing frame the compose path never displayed; the overlay's pre-quantization `startSeconds` also disagreed with the quantized segment start by up to half a frame, causing the compose-time `segStart - ov.startSeconds` seek to go slightly negative on the overlay's first segment. Both are now exact. Regression coverage added: `test/segment-plan.test.mjs` asserts every produced segment's start/end/duration sits on the frame grid given sub-frame boundary input (`1.875`, `4.7177`, `8.0000`); `test/render-helpers.test.mjs` asserts `collectPuppeteerSegments` quantizes `startSeconds`, `endSeconds`, and `frameCount` for a `5.4474 → 8.9474` overlay. All 22 segment-plan + render-helpers tests pass. No project.json schema change; existing projects re-render with the fix transparently.

Net result: audio renders cleanly from iPhone clips even when the apac stream is present in the source.

### Fixes (caught during carousel work)
- **SSE multi-line frames.** `PUT /api/projects/{id}` and three sibling endpoints were publishing `f"data: {indent=2 JSON}\n\n"` over SSE. SSE requires a `data:` prefix per line, so the browser parser was splitting on every newline inside the JSON and logging `[sse] malformed project frame: {`. The optimistic instant-update was being dropped and the UI was relying on the watcher's later (single-line) re-broadcast to catch up. New `_sse_data_frame()` helper canonicalizes any payload to a single `data:` line; all four publish sites switched over.
- **Overlay compiler tolerates named exports.** `overlay-eval.ts` only rewrote `export default …` and let bare `export const X` / `export function X` / `export { X }` survive into `new Function(...)`, throwing `Unexpected token 'export'`. The browser preview broke for any overlay that exported anything other than the default component (e.g. an overlay declaring `export const staticFrame = 30` for the carousel renderer's static-frame default). Render path was unaffected (esbuild handled it). The compiler's normalize pass now strips the `export` keyword from named declarations and drops bare `export { ... }` lines.
- **Render dispatch by project type.** `POST /api/projects/{id}/render` hardcoded `render.js`, so calling it on a carousel project ran the video renderer (producing `final.mp4` from zero segments).
